# Руководство по стилю документации

Обновлено: 2026-07-13.

Этот документ устанавливает единые требования ко всем Markdown-файлам проекта. Цель — сделать документацию понятной человеку, который впервые видит Hugo, Netlify или структуру Aerocool Ukraine.

## 1. Основные требования

Каждый действующий документ должен быть:

- написан на русском языке;
- понятен новичку без знания истории проекта;
- строго структурирован;
- синхронизирован с фактическим кодом и конфигурацией;
- датирован;
- связан с соседними руководствами переносимыми Markdown-ссылками;
- свободен от неподтвержденных обещаний и устаревших слов `текущий` или `актуальный`.

Английский сохраняется только внутри официальных названий технологий, файлов, команд, полей, API, статусов и терминов без точного русского эквивалента: Hugo, Tailwind CSS, Netlify, schema.org, Core Web Vitals, `front matter`, `canonical`, `hreflang`. Самостоятельные английские инструкции и поясняющие абзацы запрещены.

При первом употреблении редкого термина дайте короткое объяснение. Например: `page bundle` — папка Hugo, в которой Markdown и изображения одной страницы хранятся вместе.

## 2. Обязательное начало файла

Действующее руководство начинается так:

```markdown
# Название документа

Обновлено: 2026-07-13.

Кратко: зачем нужен документ и кому его читать.
```

Аудит начинается так:

```markdown
# Название аудита

Дата проверки: 2026-07-13.
Статус: текущий полный аудит.
```

Старый аудит должен прямо сообщать, что он является историческим снимком, если его имя содержит `current` или текст может быть ошибочно принят за действующее состояние.

## 3. Заголовки

Используйте обычный русский sentence case:

- правильно: `## Как запустить локальную сборку`;
- неправильно: `## Как Запустить Локальную Сборку`.

Правила:

- один `H1` на файл;
- уровни не пропускаются: после `H2` идет `H3`, а не `H4`;
- заголовок описывает содержание раздела;
- названия технологий и файлов сохраняют официальное написание;
- номер раздела допустим, если документ длинный и порядок важен.

## 4. Структура объяснения

Для процедуры используйте последовательность:

1. Цель.
2. Предварительные условия.
3. Команда или действие.
4. Ожидаемый результат.
5. Способ проверки.
6. Типичная ошибка или ограничение, если оно действительно важно.

Не давайте новичку команду без объяснения результата. Не скрывайте обязательный шаг в примечании после длинного блока.

## 5. Термины, команды и пути

Оформляйте обратными кавычками:

- команды: `npm run build`;
- пути: `layouts/_partials/`;
- поля: `schema_types`;
- значения конфигурации: `development`;
- имена функций и переменных: `REVIEW_EMAIL_HASH_SALT`.

Пользовательские надписи сайта можно выделять кавычками или жирным начертанием. Не оформляйте обычные русские слова как код.

В документации допустимы полные многострочные команды в fenced code block. В публичном `content/**/*.md` действуют отдельные редакционные правила проекта.

## 6. Списки и таблицы

- Нумерованный список используйте для последовательных действий.
- Маркированный список используйте для независимых фактов.
- Таблицу используйте для сравнения однотипных значений.
- Один пункт должен выражать одну законченную мысль.
- Не создавайте глубоко вложенные списки; разделите материал подзаголовками.

## 7. Нумерация файлов

Префикс имени показывает глобальный порядок чтения:

```text
01-documentation-map.md
02-documentation-style-guide.md
...
99-2026-07-10-full-documentation-project-sync-audit-current.md
100-2026-07-13-full-documentation-project-sync-audit-current.md
```

Текущая модель:

- `01–41` — постоянные руководства;
- `42–99` — исторические аудиты;
- `100` — текущий полный аудит.

Минимальная ширина префикса — две цифры, а не жесткий лимит в две цифры. После `99` используются `100`, `101` и далее.

CSV-приложение может иметь тот же номер и основу имени, что и родительский Markdown-документ. Оно не является отдельным шагом чтения.

Если добавляется новое постоянное руководство, его нужно разместить перед архивом аудитов. При необходимости архив механически перенумеровывается, а все точные ссылки проверяются. Нельзя снова смешивать действующие регламенты с аудитами только ради сохранения старых номеров.

## 8. Действующие документы и аудиты

Действующий документ отвечает на вопрос: «Как проект должен работать сейчас?»

Аудит отвечает на вопрос: «Что было обнаружено в конкретную дату?»

Поэтому:

- правила и команды живут в документах `01–41`;
- аудит хранит доказательства, оценку и выявленные на дату дефекты;
- старый аудит не используется как единственный источник текущего стандарта;
- исправленный дефект не удаляется из исторического аудита, но в нем можно добавить датированное примечание о последующем исправлении;
- только последний проверенный полный аудит называется текущим в карте, README и AGENTS.

## 9. Факты, даты и источники

Перед изменением числового или технического утверждения проверьте его в первичном источнике:

- версию проекта — в `mise.toml`, `package.json`, lock-файле или `netlify.toml`;
- фактическое поведение — в шаблоне, функции или собранном HTML;
- правила Hugo, Google, Chrome и Netlify — в официальной документации;
- количество файлов — командой по текущему рабочему дереву;
- состояние опубликованного сайта — по реальному URL.

Для изменчивых внешних правил указывайте дату проверки и ссылку на официальный источник. Формулируйте границы точно: `llms.txt` может быть вспомогательной картой для некоторых AI-агентов, но Google Search не считает его сигналом ранжирования.

Не пишите `соответствует лучшим практикам`, если не указано, что именно проверено и каким источником подтверждено.

## 10. Ссылки

Внутри `docs/` используйте относительные Markdown-ссылки:

```markdown
[руководство по изображениям](../content/34-image-design-playbook-2026.md)
```

Из корневого README допустим путь от корня:

```markdown
[карта документации](docs/01-documentation-map.md)
```

Не используйте абсолютные локальные пути вида `/Users/name/project/...` внутри репозитория. После переименования файла найдите все его старые имена через `rg` и проверьте цели ссылок программно.

## 11. Язык и литературная обработка

- Пишите короткими прямыми предложениями.
- Сначала сообщайте вывод, затем объясняйте причину.
- Используйте нейтральное или вежливое обращение на «вы»; не переходите на разговорное «ты» в инструкциях.
- Избегайте англоязычных канцеляризмов: вместо `code revalidation` пишите `повторная проверка кода`, вместо `screenshot evidence` — `скриншоты, подтверждающие вывод`.
- Не переводите точные имена API, полей и файлов.
- Не повторяйте один регламент в README, AGENTS и нескольких документах. Назовите источник правды и дайте ссылку.
- Не используйте рекламные формулировки в технических инструкциях.
- Не обещайте SEO-результат, который нельзя гарантировать.

## 12. Алгоритм обновления документации

1. Определите изменившийся код, контент или внешний стандарт.
2. Найдите постоянный документ `01–41`, который отвечает за это поведение.
3. Сверьте утверждение с проектом и официальным первичным источником.
4. Обновите текст и дату документа.
5. Проверьте README, AGENTS и карту только на необходимые ссылки и краткие статусы.
6. Найдите устаревшие формулировки по всему репозиторию через `rg`.
7. Проверьте локальные Markdown-ссылки.
8. Запустите релевантную сборку и `git diff --check`.
9. Создавайте новый аудит только после завершения фактической проверки.

## 13. Минимальный контроль после правок

```bash
npm run docs:check
rg -n '^#{1,6} ' README.md AGENTS.md docs
rg -n 'Обновлено:|Дата проверки:' README.md AGENTS.md docs
git diff --check
./scripts/script_check.sh
npm run build:production
```

Дополнительно нужно проверить:

- отсутствие битых относительных Markdown-ссылок;
- уникальность и последовательность числовых префиксов;
- отсутствие ссылок на удаленные имена файлов;
- отсутствие слова `текущий` рядом с устаревшим аудитом без даты и пояснения;
- совпадение версий в `mise.toml`, `package.json`, `netlify.toml`, README и AGENTS.

Команда `npm run docs:check` автоматически проверяет непрерывность и уникальность номеров, один H1, порядок уровней заголовков, дату, архивную оговорку, присутствие файлов и архивов исходников в карте, существование локальных целей Markdown-ссылок, отсутствие `.DS_Store` и машинно-зависимых путей в действующих документах.

## 14. Запрещенные практики

- Документ без H1 и даты.
- Заголовки в искусственном Title Case.
- Английский абзац без необходимости.
- Команда без ожидаемого результата.
- Текущая оценка, скопированная из старого аудита.
- Ручное редактирование сгенерированного отчета без понимания генератора.
- Дублирующая шпаргалка вне карты документации.
- Указание `immutable` для стабильного URL только потому, что Netlify deploy является атомарным.
- Представление экспериментального WebMCP или `llms.txt` как гарантированного SEO-фактора.
