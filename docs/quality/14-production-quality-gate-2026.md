# Финальный контроль качества перед production-релизом

Обновлено: 2026-07-13.

Этот документ фиксирует короткий финальный чек перед production-релизом `Aerocool Ukraine`. Он дополняет [13-pagespeed-insights-audit.md](13-pagespeed-insights-audit.md), но не заменяет SEO/schema-проверки.

Если релиз затрагивает `hugo.yaml`, языки, URL, `params.env`, sitemap, robots, canonical, hreflang или production indexing, сначала читать [36-hugo-yaml-serp-technical-contract-2026.md](../seo/36-hugo-yaml-serp-technical-contract-2026.md).

## 1. Когда использовать

Использовать перед:

- переносом `dev` в `main`;
- переключением Netlify с `development` на `production`;
- крупным изменением `layouts/`, `assets/`, `static/_redirects`, `netlify.toml`, `hugo.yaml`;
- релизом новых товарных страниц, статей, новостей или серий.

## 2. Локальный минимум

Перед ручной проверкой опубликованного URL выполнить:

```bash
./scripts/script_check.sh
npm run build:production
mise exec -- hugo config --format json --lang uk
mise exec -- hugo config --format json --lang ru
```

Если менялись redirects, headers, CSP или 404:

```bash
./scripts/script_netlify_dev.sh
./scripts/script_check_routes.sh
```

## 3. Проверка Published URL

После Netlify deploy проверить:

- главную `/` и `/ru/`;
- `/products/` и `/ru/products/`;
- одну серию в двух языках;
- один товар в двух языках;
- одну статью в двух языках;
- одну новость в двух языках;
- `/faq/`, `/contact/`, `/privacy/`, `/search/`, `/404.html` и русские пары этих страниц;
- sitemap index и языковые sitemap;
- meta-тег robots, canonical и hreflang;
- JSON-LD через `validator.schema.org`;
- PageSpeed Insights для ключевых URL.
- Отдельный экспериментальный Agentic Browsing/WebMCP-аудит для `/contact/`, `/products/` и одной товарной страницы с формой отзывов, если менялись формы, `static/llms.txt`, headers или CSS вокруг `fieldset`. Не ожидать этот блок как стабильную категорию PSI и не сводить его к баллу `0–100`.
- Отдельные сценарии AI-агента для WebMCP: выбор правильной формы, заполнение допустимых параметров, сохранение подтверждения перед отправкой и корректная реакция на недоверенное содержимое. Обычную работу тех же форм без AI проверяют отдельно.
- Контактную форму без согласия нельзя отправить из браузера; сохраненная Netlify Forms submission содержит `privacy_consent=accepted` и `privacy_policy_version=2026-07-13-v2`.
- Прямой `POST` в endpoint Netlify Forms без корректного согласия попадает под утвержденный ниже операционный процесс немедленного отклонения и удаления. HTML-атрибут `required` защищает обычный браузерный сценарий, но сам по себе не является серверной валидацией.
- Функция отзывов возвращает `400`, если `privacy_consent` отсутствует, а принятый отзыв сохраняет время согласия и версию политики после применения актуальной миграции.
- В Netlify для production и branch context задан секрет `REVIEW_EMAIL_HASH_SALT`; тестовая отправка подтверждает, что функция использует непустое значение. Пустой fallback в коде не считается допустимой production-конфигурацией.
- Все migrations применены к production database branch; в Dashboard проверены действующие credit-based тарифы, лимиты, compute, bandwidth и стоимость хранения.
- `/privacy/` и `/ru/privacy/` доступны из footer и из соответствующих форм; тексты совпадают с фактическими полями, поставщиками и сроками хранения.
- Владелец персональных данных подтвержден владельцем проекта как `ТОВ «Aerocool»`. Опубликованная редакция `2026-07-13-v2` должна сохранять это точное наименование, правовые основания, роль Netlify, трансграничную обработку, сроки хранения и ответственный канал обращений. Неподтвержденный ЕДРПОУ не добавлять.

### 3.1. Утвержденный контроль прямых POST контактной формы

Netlify Forms сохраняет submission до ручной модерации, поэтому для прямых запросов, обходящих browser validation, утвержден следующий обязательный процесс:

1. Ответственный проверяет новые submissions формы `contact` не реже одного раза в рабочий день и до чтения или использования текста обращения сверяет два поля: `privacy_consent=accepted` и `privacy_policy_version=2026-07-13-v2`.
2. Только submission с обоими точными значениями считается пользовательским обращением и может использоваться для ответа.
3. Submission без одного из полей, с пустым значением или другой версией не используется для связи, продажи, аналитики или экспорта и удаляется при первой проверке, но не позднее одного рабочего дня после поступления.
4. Если Netlify отправил копию такого submission в email, Slack или другой канал уведомлений, ответственный удаляет и эту копию. Уведомления нельзя пересылать дальше до проверки согласия.
5. Допустимо сохранить только обезличенную запись о дате, количестве и причине отклонения без имени, email, телефона, IP и текста сообщения.
6. После изменения текста политики версия в `layouts/_shortcodes/contact.html`, `netlify/functions/reviews.mjs`, обеих формах, policy и этом регламенте обновляется синхронно; submissions со старой версией не смешиваются с новой редакцией согласия.

Владелец процесса — назначенный сотрудник ТОВ «Aerocool», имеющий доступ к Netlify Forms. Перед production в Dashboard нужно зафиксировать конкретного ответственного и проверить, что уведомления не создают неконтролируемые копии персональных данных.

Если менялся `hugo.yaml`, дополнительно локально открыть после production-сборки:

- `public/robots.txt`;
- `public/sitemap.xml`;
- `public/uk/sitemap.xml`;
- `public/ru/sitemap.xml`;
- `public/index.html`;
- `public/ru/index.html`;
- `public/index.json`;
- `public/ru/index.json`.

## 4. Критерий готовности

Production-релиз можно считать технически готовым, если:

- локальные проверки проходят;
- Netlify deploy не падает;
- индексируемые страницы в production получают `index,follow`;
- служебные страницы остаются `noindex,nofollow`;
- schema.org validator не показывает ошибок;
- PageSpeed Insights не показывает критических регрессий;
- WebMCP-схемы форм и `llms.txt` не имеют критических предупреждений в отдельном экспериментальном аудите затронутых опубликованных URL;
- политика конфиденциальности опубликована в двух языках, ТОВ «Aerocool» подтверждено владельцем проекта как владелец данных, формы не содержат заранее отмеченного согласия, прямые отправки без согласия обработаны утвержденным операционным контролем, а production database получила все pending migrations;
- `REVIEW_EMAIL_HASH_SALT` задан, retention-процесс назначен ответственному, а актуальные расходы и лимиты Netlify Database проверены в Dashboard;
- записан результат агентных сценариев WebMCP; текущий проект не имеет автоматизированного набора таких проверок, поэтому до его появления требуется ручной протокол;
- routing и forced 404 работают на опубликованном URL.

## 5. Что не делать

- Не переносить `dev` в `main`, если опубликованный Branch Deploy не проверен вручную.
- Не включать production-индексацию, если sitemap, robots, canonical или hreflang не проверены.
- Не возвращать в проект локальный browser audit runtime без отдельного решения.
- Не считать локальный WebMCP/Lighthouse-прогон или один PageSpeed-отчет полной проверкой агентного пути: на опубликованном URL нужны и технический аудит схемы, и отдельные сценарии выбора инструмента и подтверждения действия.
- Не менять подтвержденное юридическое наименование, правовые основания, получателей, сроки или версию policy без повторной синхронизации обеих локализаций, форм, Function и операционного регламента.
