Обновлено: 2026-07-13.

Этот документ является главным источником правил по внутренней перелинковке, внешним ссылкам, анкорам, глубине страниц и контролю ссылочного графа проекта `Aerocool Ukraine`.

Он одновременно фиксирует:

- текущее состояние production-сборки;
- постоянные правила для новых страниц и шаблонов;
- границы между глобальными, контекстными ссылками и ссылками в блоках связанных материалов;

- приоритеты дальнейшего улучшения;
- проверки перед production-релизом.

Документ не обещает конкретную позицию в Google. Ссылки помогают обходу, пониманию структуры и распределению относительной важности страниц, но итог зависит также от индексации, контента, предложения, внешних сигналов и конкурентов.

## 2. Официальные принципы Google на 2026 год

Текущая система проекта сверена с официальными документами Google Search Central, доступными и актуальными на 2026-07-13.

Основные принципы:

1. Внутренняя ссылка должна быть обычным HTML-элементом `<a>` с реальным `href`.
2. Анкор должен быть кратким, описательным и понятным без необходимости угадывать страницу назначения.
3. Важная страница должна иметь хотя бы одну ссылку с другой страницы сайта.
4. Универсального правильного количества ссылок на странице не существует.
5. Категории должны вести ко всем товарам, которые нужно обнаружить и индексировать.
6. Относительная важность страницы зависит в том числе от количества входящих ссылок и глубины перехода.
7. Пагинация должна использовать отдельные URL и последовательные ссылки, доступные для сканирования.
8. Внешние ссылки допустимы и полезны, когда дают пользователю источник или дополнительный контекст.
9. `nofollow` не нужно автоматически добавлять всем внешним ссылкам; для рекламы используется `sponsored`, для пользовательских ссылок — `ugc` или `nofollow`.
10. `noindex` исключает страницу из результатов Google после повторного обхода независимо от качества внутренних ссылок.

Официальные источники находятся в разделе 17.

## 3. Охват и методика аудита

Аудит выполнен по свежей локальной сборке:

```bash
npm run build:production
```

Проверены:

- весь `public/**/*.html`;
- обычные страницы, хабы, серии, товары, статьи и новости;
- UK и RU версии;
- шапка сайта, мобильное меню, подвал и хлебные крошки;
- карточки листингов и товарные карточки;
- контекстные ссылки внутри основного содержимого;
- блоки `Что посмотреть дальше`;
- пагинация и `/page/1/` aliases;
- canonical, sitemap и взаимные `hreflang`;
- переключатели вариантов;
- ссылки страницы на саму себя из текущего состояния интерфейса;
- ссылки на локальные `#fragment`, `mailto:` и `tel:`;
- внешние ссылки;
- действующие `robots` и canonical главной страницы.

Ограничения аудита:

- данные Google Search Console и журналы сканирования не подключены;
- отдельный автоматический отчет по всему ссылочному графу в проекте не генерируется: после production-сборки нужен ручной контроль;
- метрики кликов пользователей и вспомогательных конверсий отсутствуют;
- относительный SEO-вес ссылки нельзя измерить одной локальной метрикой.

## 4. Текущее ограничение развертывания

Структурная перелинковка проходит текущую локальную проверку: основные страницы имеют доступные входы, товары связаны с каталогом и сериями, локальные фрагменты существуют, а UK/RU-маршруты согласованы. Числовая оценка приводится только в [текущем полном аудите](../01-documentation-map.md#5-текущий-аудит), чтобы постоянный регламент не хранил устаревший балл.

Подтвержденная проверка основного домена 2026-07-13 зафиксировала на `https://aerocool.ua/`:

```html
<meta name="robots" content="noindex,nofollow">
```

Причина закреплена в [netlify.toml](../../netlify.toml): общий build command использует `hugo --environment development`, а `HUGO_ENVIRONMENT` равен `development`.

Это не дефект внутреннего графа, но критическое ограничение развертывания: поисковик не сможет реализовать SEO-эффект даже сильной перелинковки, пока production остается закрытым.

## 5. Текущий проверяемый минимум

Production-сборка от 2026-07-13 содержит:

| Метрика | Результат |
|---|---:|
| HTML-файлы, включая служебные страницы и aliases | **134** |
| Основные индексируемые canonical URL | **98** |
| Украинские / русские основные URL | **49 / 49** |
| JSON-LD scripts на основных страницах | **98** |

Эти числа являются снимком состояния, а не постоянным нормативом. После добавления, удаления или переименования страницы их нужно пересчитать. Подробные счетчики анкоров, фрагментов и типов ссылок относятся к аудитам, потому что быстро устаревают и не должны дублироваться в постоянном контракте.

Постоянный критерий качества важнее абсолютного количества ссылок:

- у каждой индексируемой страницы есть хотя бы один доступный для сканирования вход;
- внутренние ссылки ведут сразу на canonical URL;
- UK/RU-пары не смешивают языковые маршруты;
- локальные фрагменты указывают на существующие `id`;
- отсутствуют пустые `href`, `href="#"` и `javascript:`;
- sitemap, canonical и взаимные `hreflang` согласованы.

## 6. Реализованная архитектура ссылок

### Шапка сайта и мобильное меню

[header.html](../../layouts/_partials/header.html) дает доступные для сканирования входы в:

- каталог;
- SKY;
- WING;
- XTAL;
- страница о бренде;
- статьи;
- новости;
- FAQ;
- контакты.

Выпадающий каталог для компьютеров и группа каталога в мобильном меню используют обычные `<a href>`. JavaScript управляет только поведением интерфейса и не является единственным источником URL.

### Подвал сайта

[footer.html](../../layouts/_partials/footer.html) содержит основные разделы, серии и пять внешних соцпрофилей.

Глобальный слой шапки и подвала повторяется на большинстве страниц и поэтому естественно доминирует в общем числе ссылок. Его нельзя расширять для каждого нового SEO-приоритета: новые важные связи добавляются прежде всего в основное содержимое или тематические блоки связанных материалов.

### Хлебные крошки

[breadcrumbs.html](../../layouts/_partials/breadcrumbs.html) строит видимую иерархию:

```text
Главная -> раздел -> серия -> товар
```

Название каждого узла приходит из [breadcrumb-label.html](../../layouts/_partials/breadcrumb-label.html), поэтому видимые хлебные крошки и schema.org `BreadcrumbList` используют единое правило названий.

### Каталог и серии

[products/list.html](../../layouts/products/list.html) и [products/card.html](../../layouts/_partials/products/card.html) обеспечивают прямые ссылки:

- `/products/` -> все **12** товаров текущего языка;
- `/products/sky/` -> **2** модели;
- `/products/wing/` -> **5** моделей;
- `/products/xtal/` -> **5** моделей.

Фильтры и сортировка работают по принципу `static-first` и не создают индексируемые URL фильтров. Это предотвращает дубли и ловушки сканирования.

### Варианты товаров

[variant-swatches.html](../../layouts/_partials/products/variant-swatches.html) связывает реальные варианты одной модели через `product_group_id`.

Проверено **16** страниц групп вариантов двух языков. Каждый участник группы имеет ссылку на соседний вариант. Одиночные товары не получают искусственный `product_group_id`.

### Статьи и новости

Хабы `/articles/` и `/news/` используют доступные для сканирования карточки и пагинацию. В основном содержимом материалов присутствуют ссылки на:

- серии;
- товары;
- сравнения;
- FAQ;
- контакты;
- соседние гайды.

### Блок связанных материалов

[post-footer-navigation.html](../../layouts/_partials/post-footer-navigation.html) строит блок `Что посмотреть дальше` для товаров, статей и новостей.

Источники сигналов:

- `related_series`;
- `related_products`;
- `related_articles`;
- `related_news`;
- category/categories/tags;
- `product_group_id`;
- `about_entities`;
- резервное определение серии по структурированному тексту страницы.

Явные поля `related_*` ставятся первыми, но не заменяют видимую контекстную причину связи в тексте страницы.

## 7. Глубина и доступность страниц

Для каждого языка:

| Глубина | Количество URL |
|---|---:|
| Главная | **1** |
| 1 клик | **20** |
| 2 клика | **28** |
| Более 2 кликов | **0** |

Если исключить шапку и подвал и учитывать только основное содержимое, все коммерческие и редакционные URL также находятся не глубже двух кликов. Страницы `/image-license/`, `/privacy/` и их русские версии доступны через подвал. Для таких trust pages, то есть страниц доверия и юридической информации, это допустимо и не требует искусственных контекстных ссылок.

## 8. Распределение входящих ссылок

Для оценки учитываются уникальные индексируемые источники в основной области страницы. Количество входящих ссылок не является самостоятельной целью: одна понятная контекстная ссылка полезнее нескольких механических повторов.

Обязательный минимум:

- новый товар получает входы из каталога и своей серии;
- серия получает входы из каталога и тематических материалов;
- статья или новость связана хотя бы с одним релевантным хабом, товаром, серией или соседним материалом;
- trust page доступна из постоянной служебной навигации;
- UK/RU-пары имеют сопоставимую архитектуру, но перевод не обязан повторять анкор дословно.

Точные минимумы, медианы и максимумы по типам URL пересчитываются в полном аудите. Их нельзя переносить в новые требования без проверки свежей production-сборки.

## 9. Контракт анкоров

Каждый анкор должен:

- описывать страницу назначения;
- оставаться естественным для текущего предложения;
- быть достаточно коротким;
- не повторять механически один коммерческий ключ;
- быть понятным при чтении без соседнего текста;
- совпадать с языком текущей страницы.

Допустимые примеры:

- `порівняння SKY Light і SKY 360`;
- `гид по механизмам SYNC4 и SYNC5`;
- `Aerocool WING Racer Black`;
- `контакти Aerocool Україна`.

Нежелательные примеры без уточнения назначения:

- `здесь`;
- `читать`;
- `подробнее`;
- `перейти`;
- `статья`.

Товарная карточка визуально сохраняет короткий призыв `Подробнее` / `Детальніше`, но его доступное имя включает `$page.Title` через `sr-only`. Проверка должна подтверждать, что короткий видимый CTA не остается единственным доступным названием ссылки.

`sr-only` используется только для честного доступного имени элемента. Запрещено помещать туда списки ключевых слов или текст, которого пользователь не ожидает от ссылки.

### Разнообразие анкоров

Частые значения `WING`, `XTAL` и `SKY` допустимы: это естественные названия сущностей и серий, а не искусственные коммерческие анкоры с точным вхождением.

Анкорное разнообразие оценивается по смыслу, а не по требованию каждый раз писать новую формулировку. Название товара или серии можно повторять, если оно точно описывает назначение ссылки.

### Ссылки страницы на саму себя

Ссылки на текущую страницу могут появляться в переключателе языка, активной навигации, пагинации и переключателе вариантов `ProductGroup`. Это не создает ловушку сканирования, но не должно использоваться для искусственного увеличения числа ссылок.

Для более чистой семантики текущее состояние можно выводить как `span` или другой неинтерактивный элемент с доступным обозначением. Такое изменение допустимо только после проверки клавиатурной навигации и screen reader, то есть программы экранного доступа.

### Фрагменты, электронная почта и телефон

Каждая локальная ссылка `#fragment` должна вести на существующий `id` целевой страницы. Пустые `href`, ссылки-заглушки `href="#"` и `javascript:` запрещены.

Для `mailto:` и `tel:` видимый адрес или номер должен совпадать с назначением ссылки. После изменения контактов проверяются обе локализации и все повторения в шаблонах.

## 10. UK/RU-паритет

Текущая production-сборка содержит **98** основных canonical URL: по **49** для украинской и русской версий. Ошибки графа и взаимного `hreflang` проверяются заново после каждого изменения URL.

Обязательные правила:

1. UK-страница ссылается на UK URL без `/ru/`.
2. RU-страница ссылается на соответствующий `/ru/` URL.
3. Front matter `related_*` хранит языконезависимые пути контента; шаблон подставляет язык.
4. При ручной Markdown-ссылке обе языковые версии редактируются одновременно.
5. Переключатели вариантов и хлебные крошки строятся из страниц текущего языка.
6. После изменения URL нужно проверить canonical, hreflang, sitemap и обе версии всех входящих ссылок.

`hreflang` выводит пары `uk-UA` и `ru-UA` для локализованных страниц. `x-default` сейчас не используется и не является обязательным для текущей архитектуры с украинской версией по умолчанию.

## 11. Пагинация

Текущая реализация:

- страницы `/page/2/`, `/articles/page/2/`, `/news/page/2/` имеют собственные URL;
- переходы между страницами выводятся обычными `<a href>`;
- страницы пагинации имеют canonical на самих себя;
- страницы 2+ получают `noindex,follow`;
- alias URL `/page/1/` получают canonical на первую страницу и `noindex,nofollow`;
- фильтры и сортировка не меняют URL.

В production-сборке aliases вида `/page/1/` закрыты от индексации и канонизированы на первый листинг. Страницы 2+ имеют canonical на самих себя, но остаются `noindex,follow`.

Google рекомендует отдельный URL и canonical на саму себя для каждой страницы пагинации. Текущий `noindex,follow` является сознательной проектной политикой, но его нужно пересмотреть при росте каталога или архива: для длинных последовательностей индексируемая пагинация с canonical на саму себя может быть более устойчивым способом обнаружения страниц.

Сейчас все **98** основных URL находятся в sitemap, а целевые страницы доступны через категории и последовательные ссылки.

## 12. Внешние ссылки

В подвале используются ссылки на официальные профили:

- Facebook;
- Instagram;
- TikTok;
- YouTube;
- X.

Footer использует:

```html
target="_blank" rel="noopener noreferrer me"
```

Это корректно для безопасности новой вкладки и связи с официальным профилем. Доступность и принадлежность внешних URL нужно проверять перед production-релизом: прежний успешный HTTP-ответ не гарантирует их текущее состояние.

В редакционных статьях сейчас нет обычных внешних ссылок на источники. Массово добавлять их не нужно. Ссылки на внешние первичные источники полезны там, где текст опирается на технический стандарт, исследование, медицинское ограничение или официальную документацию производителя.

Правила:

- не добавлять внешнюю ссылку только ради SEO;
- объяснять пользователю, куда ведет ссылка;
- не использовать `nofollow` для доверенного источника без причины;
- использовать `sponsored` для оплаченной ссылки;
- использовать `ugc` или `nofollow` для пользовательских ссылок;
- регулярно проверять переадресации, ответы 404 и смену владельца домена.

URL schema.org, пространства имен XML, `@id` и `sameAs` внутри JSON-LD не являются обычными видимыми ссылками и проверяются отдельным процессом schema.org и сущностей.

## 13. Что нельзя делать

- Добавлять каждую приоритетную страницу в подвал.
- Создавать скрытые списки коммерческих анкоров.
- Использовать навигацию только через JavaScript без реального `href`.
- Ссылаться на `/page/1/`, alias URL или URL переадресации.
- Вести украинскую страницу на русский URL и наоборот без переключателя языка.
- Добавлять десятки нерелевантных ссылок в блок связанных материалов.
- Создавать индексируемые URL фильтров и сортировки без отдельной SEO-стратегии.
- Добавлять `product_group_id` одиночному товару ради ссылок между вариантами.
- Использовать одинаковый анкор с точным вхождением во всех входящих ссылках.
- Считать sitemap заменой внутренней навигации.
- Считать количество ссылок самостоятельной целью.

## 14. Приоритеты после аудита

### P0. Индексируемость production-сборки

Настроить отдельный Netlify production context с `hugo --environment production`, сохранив `development` и `noindex,nofollow` для `dev` Branch Deploy.

После production-развертывания проверить:

- главную;
- каталог;
- серию;
- товар;
- статью;
- новость;
- UK/RU пару;
- индекс sitemap.

### P1. Ручной аудит ссылочного графа

Статус: активный постоянный процесс.

После production-сборки проверять вручную:

- неработающие ссылки;
- страницы без входящих ссылок;
- ссылки на alias URL и переадресации;
- расхождения canonical и sitemap;
- пустые и неинформативные анкоры;
- глубину более трех кликов;
- UK/RU-паритет;
- прямую доступность всех товаров из каталога и серий;
- ссылки внутри групп вариантов;
- взаимные `hreflang`;
- неработающие `#fragment`, некорректные `mailto:` и `tel:`;
- лишние ссылки страницы на саму себя из текущего состояния;
- ошибки HTTP у внешних ссылок.

Историческая исходная ручная проверка зафиксирована в [аудите `87`](../audits/87-2026-06-24-full-link-content-seo-audit.md): на 2026-06-24 было 0 битых внутренних ссылок, 0 сломанных фрагментов, 0 страниц без входящих ссылок, 0 расхождений sitemap/canonical и 0 ошибок `hreflang`. Последняя полная проверка указана в [карте документации](../01-documentation-map.md#5-текущий-аудит).

### P2. Политика пагинации

До существенного роста каталогов и архивов принять отдельное решение по страницам пагинации 2+. Наиболее близкий к рекомендации Google вариант — `index,follow` с canonical на саму себя для последовательных URL листинга. Если сохраняется `noindex,follow`, это должно оставаться осознанной политикой с контролем обнаружения через Search Console и журналы сканирования.

### P2. Редакционные внешние источники

Для новых технических утверждений добавлять ссылку на официальную спецификацию товара, стандарт или первичное исследование, если без нее утверждение нельзя проверить. Не создавать массовый блок внешних ссылок на всех страницах.

### P2. Приоритетные товары на главной

Если бизнес-команда подтвердит лидеров продаж или стратегические SKU, можно вывести 2-4 прямые ссылки с главной. Не выбирать товары автоматически по неподтвержденному рейтингу или временной позиции в списке.

### P3. Проверка в Search Console

После включения индексации использовать реальные данные:

- усиливать URL с показами и позициями примерно 8-20;
- смотреть расхождения между запросом и целевой страницей;
- оценивать изменение показов, кликов и средней позиции;
- не менять одновременно все кластеры без возможности сравнить результат.

### P3. Очистка ссылок страницы на саму себя

При следующей плановой правке шапки сайта, переключателя языка, пагинации или переключателей вариантов заменить ссылки текущего состояния на неинтерактивные элементы там, где переход приводит на тот же URL. Это улучшение семантики и UX, а не срочное SEO-исправление.

## 15. Чек-лист после изменения ссылок

- [ ] Обе языковые версии изменены синхронно.
- [ ] Целевой URL существует в production-сборке.
- [ ] Ссылка ведет сразу на canonical URL без переадресации.
- [ ] Анкор понятен без соседнего текста.
- [ ] Ссылка имеет реальный `<a href>`.
- [ ] Локальный `#fragment` существует в сгенерированном HTML.
- [ ] Контекст объясняет, зачем переходить.
- [ ] Новая ссылка не дублирует бессмысленно соседнюю ссылку.
- [ ] Ссылка текущего состояния не ведет без необходимости на тот же URL.
- [ ] Поле `related_*` подтверждено видимым содержанием.
- [ ] Новый товар доступен из каталога и серии.
- [ ] Новый вариант связан с группой только при реальном ProductGroup.
- [ ] Не появился новый URL фильтра или сортировки.
- [ ] Пагинация сохраняет последовательные ссылки.
- [ ] Sitemap и canonical согласованы.
- [ ] UK/RU `hreflang` взаимны и ведут на canonical URL.
- [ ] `noindex` остается только там, где это предусмотрено политикой.
- [ ] Внешняя ссылка проверена и имеет подходящий `rel`.

Минимальные действующие проверки:

```bash
./scripts/script_check.sh
npm run build:production
```

После production-сборки вручную проверять итоговый сайт: ключевые URL, sitemap, canonical, `hreflang`, локальные якоря, карточки, breadcrumbs, related-блоки и целевые страницы.

## 16. Критерии оценки

Свежая числовая оценка приводится только в [текущем полном аудите](../01-documentation-map.md#5-текущий-аудит), чтобы постоянное руководство не хранило устаревший балл.

При оценке учитываются:

- доступность HTML-ссылок для поискового робота и вспомогательных технологий;
- глубина и отсутствие индексируемых страниц без входящих ссылок;
- маршруты от каталога и серий к каждому товару;
- canonical, aliases, sitemap и взаимные `hreflang`;
- качество и языковой паритет анкоров;
- работоспособность фрагментов, `mailto:` и `tel:`;
- релевантность блоков связанных материалов;
- политика пагинации;
- состояние внешних ссылок;
- воспроизводимость контроля после каждой production-сборки.

Максимальная оценка невозможна, пока контроль всего графа остается ручным, отсутствуют реальные данные Search Console, не подтверждена production-индексация и нет наблюдения за внешними URL во времени.
