# Аудит опубликованного сайта в Google 2026

Обновлено: 2026-07-15.

Этот документ описывает проверку Aerocool Ukraine после публикации: как убедиться, что Google видит правильные URL, понимает контент и получает согласованные технические сигналы. Внутреннюю проверку локальной Hugo-сборки задает [документ 28](28-ssg-seo-checklist-2026.md), а условия включения индексации — [документ 14](../quality/14-production-quality-gate-2026.md).

Аудит не обещает позицию и не требует покупать набор SEO-сервисов. Обязательны первичные данные Google и проверка реального URL; сторонние crawler, backlink и rank-tracking tools используются только после отдельного решения о задаче, бюджете и владельце процесса.

## 1. Предварительное условие

Текущая конфигурация Netlify разделяет окружения. Production Deploy ветки `main` собирается в `production`, а Branch Deploy и Deploy Preview остаются в `development` и возвращают `noindex,nofollow`. Наличие production context в репозитории еще не доказывает, что реальный основной домен уже опубликован с правильными сигналами: это проверяется только после deploy.

Полный Google-аудит начинается после того, как:

1. Пройден production quality gate.
2. Основные страницы опубликованы с `index,follow`.
3. Canonical, hreflang и sitemap доступны на основном домене.
4. Google Search Console подтверждена владельцем сайта.
5. После deploy прошел повторный контроль реальных ответов сервера.

Если любой из этих пунктов не выполнен, в отчете ставится статус `blocked`, а не искусственная SEO-оценка.

## 2. Обязательные инструменты

| Инструмент | Что доказывает | Чего не доказывает |
|---|---|---|
| Google Search Console | Обход, индексацию, запросы, показы, клики, позиции, sitemap и улучшения | Полноту контента и удобство интерфейса |
| PageSpeed Insights | Полевые CrUX-данные, если доступны, и лабораторную диагностику Lighthouse | Индексацию, конверсию или качество текста |
| URL Inspection | Состояние конкретного URL в Google, выбранный canonical и последнюю обработку | Состояние всего сайта по одному примеру |
| Rich Results Test | Право URL претендовать на поддерживаемые Google rich results | Полную корректность всех типов schema.org |
| Schema.org Validator | Синтаксис и словарь schema.org | Соответствие разметки правилам Google и видимому контенту |
| Браузер и DevTools | Реальные headers, HTML, network, console, доступность и поведение | Полевую картину всех пользователей |

Screaming Frog, Sitebulb, Ahrefs, Semrush, Serpstat и аналоги могут ускорить отдельную работу, но не входят в зафиксированный стек проекта и не являются обязательным условием релиза.

## 3. Индексация и sitemap

### 3.1. URL Inspection

Проверить минимум:

- главную;
- `/products/`;
- одну серию;
- один товар;
- `/articles/` и одну статью;
- `/news/` и одну новость;
- `/about/`, `/contact/`, `/faq/`, `/privacy/`;
- соответствующие русские URL.

Для каждого URL записать:

| Поле | Ожидаемый результат |
|---|---|
| URL доступен Google | Да |
| Индексирование разрешено | Да для основных страниц |
| User-declared canonical | Текущий языковой URL |
| Google-selected canonical | Совпадает или имеет объяснимую причину расхождения |
| Последний обход | После актуального deploy или запрошен повторный обход |
| Page resources | Критические CSS, JS и изображения доступны |

### 3.2. Отчет Pages

- [ ] Основные canonical URL проиндексированы.
- [ ] Служебные `noindex` URL исключены по ожидаемой причине.
- [ ] Нет массового `Crawled - currently not indexed` без анализа качества.
- [ ] Нет `Duplicate, Google chose different canonical` для языковых пар.
- [ ] Нет server error, redirect error или blocked by robots.txt на важных URL.
- [ ] Число URL сравнивается с текущей production-сборкой, а не со старым аудитом.

### 3.3. Sitemaps

- [ ] Sitemap index принят Search Console.
- [ ] Языковые sitemap доступны и возвращают XML без ошибки.
- [ ] В sitemap находятся только основные canonical URL.
- [ ] `lastmod` отражает содержательные изменения.
- [ ] Search, aliases, success pages, 404 и пагинация с `noindex` не попадают в sitemap.

## 4. Canonical и hreflang

- [ ] Canonical абсолютный, использует HTTPS и основной домен.
- [ ] Украинская страница канонизируется на URL без `/ru/`.
- [ ] Русская страница канонизируется на соответствующий URL с `/ru/`.
- [ ] `hreflang="uk-UA"` и `hreflang="ru-UA"` взаимны.
- [ ] Каждая hreflang-цель отвечает `200` и имеет canonical на себя.
- [ ] Canonical не ведет с одного языка на другой.
- [ ] `x-default` отсутствует, пока нет отдельной нейтральной страницы выбора языка.
- [ ] Sitemap, HTML и Search Console показывают одну и ту же архитектуру URL.

Расхождение Google-selected canonical нельзя исправлять механическим добавлением еще одного тега. Сначала проверяются дубли контента, внутренние ссылки, redirects, язык и доступность URL.

## 5. Эффективность в Search Console

Первые выводы делаются после накопления достаточного периода, а не по одному дню.

Анализировать:

| Срез | Вопрос |
|---|---|
| Query | Соответствует ли запрос содержанию целевой страницы? |
| Page | Какая страница получает показы и не конкурирует ли она с соседней? |
| Country | Приходит ли целевая аудитория из Украины? |
| Device | Есть ли заметный провал mobile относительно desktop? |
| Search appearance | Появляются ли поддерживаемые product или merchant результаты? |
| Date | Изменился ли показатель после конкретного deploy или контентной правки? |

Не интерпретировать среднюю позицию без query/page/device. Не создавать новый URL только потому, что один запрос показался на соседней странице. Решение принимается после устойчивого паттерна и проверки интента.

## 6. Core Web Vitals и PageSpeed Insights

Главные полевые пороги Google на 75-м процентиле:

| Метрика | Хорошо |
|---|---:|
| LCP | `<= 2.5 s` |
| INP | `<= 200 ms` |
| CLS | `<= 0.1` |

Порядок проверки:

1. Сначала посмотреть полевые CrUX-данные URL или origin за 28 дней.
2. Затем использовать Lighthouse lab data для поиска причины.
3. Проверить mobile и desktop отдельно.
4. Повторить запуск несколько раз при нестабильной сети.
5. Исправлять конкретный ресурс, long task или layout shift, а не «цвет балла».

Проект не устанавливает произвольное обязательное значение Performance `95`, `100` или общий средний score. Лабораторный балл зависит от устройства и запуска; важнее отсутствие регрессии, хорошие полевые LCP/INP/CLS и понятная причина каждого отклонения.

Отдельной PWA-категории в актуальном PageSpeed Insights нет. Service worker и manifest проверяются функционально. Agentic Browsing/WebMCP остается отдельным экспериментальным аудитом и не влияет на Google ranking.

## 7. Структурированные данные Google

### 7.1. Rich Results Test

Проверить репрезентативные URL:

- товар без отзывов;
- товар с реальными approved-отзывами, когда он появится;
- группа вариантов;
- статья;
- новость;
- FAQ как семантическую разметку без ожидания FAQ rich result.

### 7.2. Сопоставление с видимым контентом

- [ ] Цена и валюта совпадают.
- [ ] Наличие совпадает.
- [ ] SKU, MPN и GTIN относятся к текущему товару.
- [ ] Доставка, возврат и гарантия видимы и согласованы с FAQ.
- [ ] `AggregateRating` и `Review` появляются только из видимых approved-отзывов.
- [ ] `ProductGroup` соответствует реальной видимой группе вариантов.
- [ ] Автор, даты и изображения Article/NewsArticle совпадают с HTML.
- [ ] BreadcrumbList совпадает с видимыми breadcrumbs.

FAQ rich results больше не являются целью Google Search с мая 2026 года. `FAQPage` можно сохранять ради честного описания видимого FAQ, но нельзя считать его будущим enhancement или KPI.

## 8. Контент и поисковый интент

Для каждой приоритетной страницы ответить:

1. Какой основной вопрос пользователя она закрывает?
2. Видит ли пользователь краткий ответ без долгого поиска по странице?
3. Есть ли подтвержденные факты, сравнения и ограничения?
4. Помогает ли текст выбрать действие, товар или следующую страницу?
5. Отличается ли страница по задаче от соседних URL?
6. Соответствуют ли title, H1, description и внутренние анкоры одному интенту?
7. Обновлены ли обе языковые версии?

Проверка конкурентов выполняется по конкретному query и стране в нейтральном режиме. Сравниваются не длина текста и число ключей, а полнота ответа, доказательства, структура товара, изображения, доверие, скорость и удобство. Не копируйте блок конкурента только потому, что он находится выше.

## 9. Товарные страницы

- [ ] Google видит отдельный canonical URL каждого товара.
- [ ] Название модели, цвет и материал однозначны.
- [ ] Цена, наличие и коммерческие условия актуальны.
- [ ] Главное изображение соответствует варианту.
- [ ] Варианты одной модели связаны видимыми ссылками и `ProductGroup`.
- [ ] Нет ручного рейтинга без отзывов.
- [ ] Merchant listing и product snippet проверяются как разные возможности Google.
- [ ] Product feed и Merchant Center добавляются только при реальном торговом процессе и владельце данных.

## 10. Изображения в Google

- [ ] Googlebot может получить основной WebP без авторизации и блокировки robots.txt.
- [ ] Основное изображение присутствует в HTML, Open Graph и `ImageObject`.
- [ ] `alt` описывает конкретный товар или сцену.
- [ ] Изображение не содержит placeholder, watermark или ложный текст.
- [ ] Article/news имеют проверенные варианты пропорций для schema.org.
- [ ] Страница лицензии доступна и не обещает несуществующее свободное использование.
- [ ] В Search Console анализируется Image search, когда данных достаточно.

Отдельный image sitemap не добавляется автоматически. Сначала нужно доказать, что текущий sitemap и доступные HTML-изображения недостаточны для реальной задачи.

## 11. Доверие, privacy и безопасность

- [ ] About объясняет бренд, локальную организацию и редакционную политику.
- [ ] Contact показывает актуальные телефон, email, адрес и часы работы.
- [ ] Privacy доступна на обоих языках и соответствует реальному сбору данных.
- [ ] Доставка, оплата, гарантия и возврат видимы до отправки формы или покупки.
- [ ] Авторство статей и новостей не выдумано.
- [ ] HTTPS и основные security headers присутствуют на реальном URL.
- [ ] Нет mixed content, открытых секретов или персональных данных в HTML.
- [ ] Контактная форма и отзывы проверяют согласие не только через browser validation.

E-E-A-T не является одним техническим тегом или числовым фактором. Для проекта это совокупность подтвержденного авторства, прозрачных условий, точных фактов, источников и безопасного пользовательского процесса.

## 12. Внутренние и внешние ссылки

### Внутренние ссылки

- [ ] Важные URL доступны через обычные `<a href>`.
- [ ] Нет индексируемых страниц без входящих ссылок.
- [ ] Анкоры описывают назначение.
- [ ] UK/RU-маршруты не смешиваются.
- [ ] Нет redirect chains, aliases или битых фрагментов.
- [ ] Related-блоки объяснимы содержанием.

### Внешние сигналы

Backlinks и брендовые упоминания оцениваются по качеству и контексту, а не по валовому количеству. Полезны официальные партнеры, профильные публикации и реальные обзоры; запрещены link schemes, массовый обмен и покупка спамных ссылок.

Платный backlink tool не является обязательным до появления ответственного процесса. Для первого цикла достаточно Search Console Links, ручной проверки бренда и подтвержденных партнерских источников.

## 13. Локальный контекст Украины

- [ ] Украинский язык остается основным.
- [ ] Русская версия имеет отдельные URL и взаимный hreflang.
- [ ] Адрес, телефон и часы работы совпадают на сайте и подтвержденных внешних профилях.
- [ ] Google Business Profile создается только при реальной подходящей бизнес-модели и ответственном владельце.
- [ ] Городские страницы не создаются без реального локального предложения и уникальной пользы.
- [ ] Доставка по Украине описана одинаково в товаре, FAQ и schema.org.

## 14. AI features и сущности

Официальное руководство Google не требует отдельного файла, специальной AI-schema или новых технических тегов для AI Overviews и AI Mode. Действуют обычные основы Search:

- разрешенный обход и индексация;
- полезный видимый контент;
- точные структурированные данные;
- качественные изображения;
- понятные сущности и внутренние ссылки.

`llms.txt` не является фактором ранжирования Google. WebMCP помогает совместимым агентам взаимодействовать с формами, но не заменяет schema.org, доступность, Search Console или server-side validation.

AI referral, citations и brand sentiment можно измерять как дополнительный канал после production-запуска. Эти показатели не смешиваются с organic clicks и не используются как доказательство причин изменения позиций.

## 15. Приоритеты дефектов

| Уровень | Пример | Действие |
|---|---|---|
| P0 | Важный URL закрыт `noindex`, canonical ведет не туда, персональные данные раскрыты | Блокировать релиз или исправлять немедленно |
| P1 | Ошибка hreflang, неверный merchant fact, плохой LCP/INP/CLS у группы URL | Исправить в ближайшем релизе с повторной проверкой |
| P2 | Слабый анкор, неполный alt, недостаточный контекст статьи | Включить в план контента или шаблонов |
| P3 | Эксперимент с новым инструментом, AI monitoring или дополнительным форматом | Делать после подтверждения пользы |

Не присваивайте P0 только потому, что сторонний сервис показал низкий собственный score. Приоритет определяется риском для индексации, пользователя, данных, дохода и достоверности.

## 16. Последовательность аудита

1. Зафиксировать deploy ID, дату, commit и проверяемое окружение.
2. Проверить robots, status, canonical, hreflang и sitemap на реальном домене.
3. Выполнить URL Inspection репрезентативных страниц.
4. Проверить Search Console Pages и Sitemaps.
5. Проверить Performance по query, page, device и country.
6. Проверить полевые Core Web Vitals, затем лабораторную причину.
7. Проверить Google rich results и соответствие schema.org видимому HTML.
8. Проверить контент, товары, изображения, доверие и privacy.
9. Проверить внутренние ссылки и подтвержденные внешние упоминания.
10. Составить список P0–P3 с владельцем и условием закрытия.
11. После исправления повторить тот же тест, а не объявлять проблему закрытой по локальному коду.

## 17. Минимальный отчет

Каждый полный аудит опубликованного сайта должен указывать:

| Поле | Содержание |
|---|---|
| Дата и окружение | Production, Branch Deploy или Deploy Preview |
| Commit/deploy | Точный идентификатор проверенной версии |
| Охват | URL и языки |
| Источник доказательства | Search Console, PSI, HTML, header или validator |
| Находка | Наблюдаемый дефект без предположения |
| Риск | Индексация, UX, данные, rich result или мониторинг |
| Приоритет | P0–P3 |
| Исправление | Конкретное действие и владелец |
| Повторная проверка | Команда, URL или отчет, который докажет закрытие |

Скриншот без даты, URL и окружения не считается воспроизводимым доказательством.

## 19. Вывод

Сильный Google-аудит не равен высокому PageSpeed score или длинному списку сервисов. Для Aerocool он считается завершенным, когда реальный production URL доступен для индексации, Search Console подтверждает ожидаемую архитектуру, полевые данные измерены, schema.org совпадает с видимым контентом, а каждое найденное отклонение имеет доказательство и условие повторной проверки.
